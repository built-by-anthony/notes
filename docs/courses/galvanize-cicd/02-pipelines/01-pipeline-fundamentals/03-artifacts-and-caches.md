# Artifacts and Caches 

## Learning Objectives 

- Decribe how ***artifacts*** are used in the `.gitlab-ci.yml` file. 
- Distinguish how ***reports*** from ordinary artifacts, and collect test results with `artifacts:reports:junit`.

## Introduction

GitLab Ci/CD provides many powerful features to help automate the prcess of building, testing, and deploying software. Two of the most important keywords in GitLab CI/CD are **artifact** and **cache**. We'll explore how to use these keywords to speed up the execution of jobs and make the deployment process smoother. 

## Artifacts

Artifacts are files that are generated by a job and can be used for debugging or analysis purposes. Artifacts can include logs, test results, compiled binaries, or any other type of file that provides insight into the job's execution. 

When a job completes, GitLab alklows you to specify which files should be considered artifacts, and these files are then upl;oaded to GitLab's artifact storage. Artifacts can then be downloadsed and viewed from within GitLab, making it easier to diagnose and fix issues with the job's execution.

### Example - Python Artifacts

Let's say we have a Python application, and we want to generate a build that we can use for deployment or testing. We can use the following `.gitlab-ci.yml` file to install dependencies, run tests, and package out application as artifacts. 

```yaml
build:
  stage: build
  image: python:3.12
  script:
    - pip install -r requirements.txt
    - pip install build
    - python -m build --outdir dist/
  artifacts:
    paths: 
      - dist/
```

### Reports - A Special Kind of Artifact

The example above uses `artifacts:paths:`, which tells GitLab ***"hold on to these files so a human can downloads them later".*** GitLab also accepts a second kind of artifact, `artifacts:reports:`, which says something different: ***"parse this file and show me the results in the UI."***

| | `artifacts:paths:` | `artifacts:reports:` |
|-|--------------------|----------------------|
|What GitLab does with the file | Store it as-is | Parses it and renders the results|
| Where you see the result | The job's **Download** button | The pipeline's **Tests** tab and the merge request widget | 
| Accepted file format | Anything | A specific format per report type | 

The most common report type is `junit`, which collects test results. Here is a Python Pytest job that saves its results both ways: 

```yaml
test-job:
  stage: test
  script:
    - pip install -r requirements.txt
    - pytest --junitxml-report.xml
  artifacts:
    when: always
    paths:
      - report.xml
    reports:
      junit: report.xml
```

**A few things worth noticing**: 

- `pytest --junitxml=report.xml` runs the Python tests and generates a JUnit XML report. 
- `paths` and `reports` can be used together in the same job. Here, the same report is both downloadable and parsed into test results. 
- `when: always` matters for test reports. By default, artifacts are only uploaded when a job succeeds, but a failing test job is exactly when you want to see which tests failed. 
- GitLab does not generate the report; it only reads it. Pytest has to create the XML file first. 

With a JUnit report in place, a failed test no longer means scrolling through the job log. GitLab lists the failing tests directly in the pipeline's **Tests** tab and, where supported, on the merge request. 

## Cache 

Cache is used to speed up the execution of jobs by allowing commonly used dependencies or large files to be stored and reused across multiple job runs.

When a job is run, GitLab checks if there is a cached version of the specified files or directories and if there is, it is used instead of downloading or generating the files again.

This can save significant time and resources, especially for large builds or deployments.

### Example - Python (Pytest)

In Python, the `PIP_CACHE_DIR` variable sets the location where pip stores downloaded packages, allowing dependencies to be reused between pipeline jobs. 

The `cache` block persists the `.cache/pip` directory across jobs, avoiding repeated downloads. 

- GitLab restores the cache before each job and updates it afterward. 
- The shared cache key (`python-pip`) esnures all jobs resuse the same cache. 
- The `python:3.21` Docker image specifies the Python version used in the pipeline. 

```yaml
stages:
  - build
  - test

variables:
  PIP_CACHE_DIR: ""$CI_PROJECT_DIR/.cache/pip"

default:
  image: python:3.12
  cache: 
    key: python-pip
    paths:
      - .cache/pip/

build-job:
  stage: build
  script:
    - pip install -r requirements.txt
    - python -m compileall . 
  artifacts:
    paths:
      - .

test-job: 
  stage: test
  script:
    - pip install -r requirements.txt
    - pytest --junitxml=report.xml
  needs: ["build-job"]
  artifacts:
    when: always
    paths:
      - report.xml
    reports:
      junit: report.xml
```

This pipeline uses Python 3.12, caches installed package downloads, and separates the build and test stages.
